重装 WSL2：从 Ubuntu 22.04 到 Ubuntu 26.04 的科研开发环境迁移

最近，我重新安装了 Windows Subsystem for Linux（WSL2），将原先的 Ubuntu 22.04 开发环境迁移到了 Ubuntu 26.04 LTS，并重新配置了 C++、CUDA、Python 和 GitHub 等科研开发工具。

这次重装的直接原因是磁盘空间。我的电脑只有一块 1 TB 的 SSD，而旧 WSL 占用了接近 500 GB。经过检查发现，问题并不完全来自 WSL 虚拟磁盘本身，而是长期积累的科研代码、编译产物和数值实验结果。

借此机会，我决定重新整理整个开发环境，并记录其中值得注意的配置细节。

1. WSL 磁盘空间分析#

首先，在旧 Ubuntu 中检查文件系统的实际占用：

df -h /
sudo du -xhd1 / 2>/dev/null | sort -h
du -h --max-depth=1 ~ | sort -h

结果显示，Linux 文件系统实际使用了约 416 GB，其中：

目录占用
/home370 GB
/usr19 GB
/opt14 GB
/var14 GB
~/AI4SciComp280 GB
~/.cache26 GB
~/anaconda322 GB

进一步检查 AI4SciComp：

du -h --max-depth=2 ~/AI4SciComp \
    2>/dev/null | sort -h | tail -50

发现 asc-cpp-evidence 单独占用了约 274 GB。

这个目录主要与此前使用 Codex 开展 C++ 开发和自动化验证有关。大量测试、实验输出及中间文件不断累积，最终形成了可观的存储开销。

这也说明，WSL 磁盘空间膨胀未必只是 ext4.vhdx 无法自动收缩的问题。对于长期运行数值实验的科研环境，实际文件占用往往更加重要。

2. 备份代码与安装新系统#

我选择全新安装 Ubuntu，而不是直接在旧系统上升级。

由于只有 C 盘，没有足够的独立空间同时保存完整系统镜像和新环境，因此优先通过 GitHub 备份重要科研代码。

备份过程中遇到了 GitHub 的大文件限制。例如：

dof.dat      181.35 MB
data.mat     279.30 MB

GitHub 普通 Git 仓库不接受超过 100 MiB 的单个文件，即使文件后来被删除，只要仍存在于待推送的 Git 历史中，也可能导致推送失败。

因此，源码和大型实验数据需要分开管理。科研源码适合使用 Git，而大型数值结果更适合独立归档，必要时使用 Git LFS 或其他存储服务。

新系统安装完成后，我将 WSL 发行版命名为 Ubuntu，并设置为默认发行版：

wsl --set-default Ubuntu

随后在 Windows Terminal 中将 Ubuntu 设置为默认终端，继续使用 Zsh 作为日常 Shell。

3. Shell 与个人开发配置#

为了方便未来迁移，我将个人 Shell 配置拆分到独立文件：

~/.config/shell/
├── aliases.sh
├── exports.sh
└── functions.sh

在 ~/.zshrc 中加载：

source "$HOME/.config/shell/exports.sh"
source "$HOME/.config/shell/aliases.sh"
source "$HOME/.config/shell/functions.sh"

这样，个人快捷命令、环境变量和自定义函数可以独立维护。

相比把所有配置都堆积在 .zshrc 中，这种方式更便于备份、复用和排查环境问题。

4. C++ 编译与构建工具#

新系统采用较新的 GNU 工具链。

目前使用的 G++ 版本为：

GCC 15.2.0

CMake 则升级到了：

CMake 4.4.4

同时安装 Ninja，作为 CMake 的主要构建后端。

对于一般 C++ 项目，可以采用：

cmake -S . -B build -G Ninja \
    -DCMAKE_BUILD_TYPE=Release

cmake --build build --parallel 4

在科研项目中，我倾向于为不同编译器、构建模式和计算后端建立独立的构建目录，避免不同配置之间的 CMake 缓存冲突。

例如：

build-gcc15/
build-debug/
build-cuda/

这样也方便开展不同编译器和构建参数的性能比较。

5. Eigen、oneMKL 与 oneTBB#

在线性代数方面，我重新安装了 Eigen，并配置了 Intel oneMKL 和 oneTBB。

Eigen 5.0.1#

Eigen 从官方 GitLab 仓库获取，使用固定版本标签：

git clone https://gitlab.com/libeigen/eigen.git
cd eigen
git checkout 5.0.1

通过 CMake 安装时，将安装前缀设置为：

/usr/local

Eigen 头文件的目标位置为：

/usr/local/include/eigen3/

在 CMake 项目中，可以使用：

find_package(Eigen3 5.0 REQUIRED NO_MODULE)
target_link_libraries(main PRIVATE Eigen3::Eigen)

Eigen 本身是仅头文件（header-only）库，不需要为了使用其 C++ 矩阵接口而构建可选的 BLAS/LAPACK 兼容库。

Intel oneMKL#

对于 BLAS、LAPACK、FFT 等高性能数值计算，我选择按需安装 Intel oneMKL，而不是完整的 oneAPI Toolkit：

sudo apt install intel-oneapi-mkl-devel

MKL 通常安装在：

/opt/intel/oneapi/mkl/latest/

需要时加载：

source /opt/intel/oneapi/mkl/latest/env/vars.sh

oneTBB#

任务并行库 oneTBB 使用 Ubuntu 软件源安装：

sudo apt install libtbb-dev

CMake 中可以通过：

find_package(TBB CONFIG REQUIRED)
target_link_libraries(main PRIVATE TBB::tbb)

使用。

最终，Eigen、oneMKL 和 oneTBB 分别负责 C++ 线性代数表达、传统高性能数值库和任务并行，三者可以根据实际算法需求组合使用。

6. CUDA 开发环境迁移#

这次迁移中，CUDA 的兼容性问题最值得记录。

我的 GPU 是 NVIDIA GeForce RTX 3060 Laptop，拥有 6 GB 显存，计算能力为 8.6。

最初使用的是：

CUDA Toolkit 12.9
GCC 15.2
Ubuntu 26.04

但编译 CUDA C++ 程序时，NVCC 直接报告：

unsupported GNU version!
gcc versions later than 14 are not supported!

尝试 GCC 14 后，又遇到了 CUDA 头文件与系统 glibc 头文件之间的数学函数声明冲突，涉及：

cospi
sinpi
rsqrt

即使通过：

-allow-unsupported-compiler

绕过 GCC 版本检查，GCC 15 的标准库仍出现 __is_pointer、__is_volatile 等编译错误。

这说明 CUDA 的兼容性不仅取决于 GCC 版本，还涉及 NVCC 编译前端、C++ 标准库以及系统 glibc。

升级 NVIDIA 驱动#

随后，我将 Windows NVIDIA 驱动升级到了较新的版本。

在 WSL 中，nvidia-smi 显示：

NVIDIA-SMI: 615.78.05
KMD Version: 617.42
CUDA UMD Version: 13.4

GPU 可以正常识别。

需要注意，WSL2 使用 Windows 侧提供的 NVIDIA 驱动，不应在 Ubuntu 内重复安装普通 Linux NVIDIA 显卡驱动。

安装 CUDA Toolkit 13.3#

在 NVIDIA 官方 WSL APT 仓库中，当时可用的最新 Toolkit 是 13.3.1。

我选择安装固定版本系列：

sudo apt install cuda-toolkit-13-3

并在 Shell 中配置：

export CUDA_HOME=/usr/local/cuda-13.3
export CUDACXX="$CUDA_HOME/bin/nvcc"
export PATH="$CUDA_HOME/bin:$PATH"

RTX 3060 对应的 CUDA 架构参数为：

-arch=sm_86

CUDA 13.3 与 GCC 15 的最小 CUDA 程序编译和运行测试是迁移后的关键验证项目。此前已经建立了测试流程，但在这份记录所依据的操作日志中，尚未看到最终成功运行的结果，因此暂不将其列为已通过测试。

7. Anaconda 与 Python 科研环境#

Python 环境继续使用 Anaconda，但将科研依赖集中到一个独立环境：

conda create -n sci python=3.12 pip
conda activate sci

基础科学计算库包括：

conda install -c conda-forge \
    numpy scipy matplotlib pandas sympy \
    h5py scikit-learn \
    jupyterlab ipykernel \
    tqdm pyyaml pytest

GPU 计算主要使用 PyTorch 和 JAX。

在升级 NVIDIA 驱动和 CUDA Toolkit 后，我进一步尝试将两个框架升级到 CUDA 13 版本。

PyTorch 使用官方 CUDA wheel，JAX 使用：

python -m pip install -U "jax[cuda13]"

需要注意，Python 框架使用的 CUDA 运行库版本不必与系统 CUDA Toolkit 的小版本完全一致。

JAX GPU 初始化问题#

JAX 升级过程中遇到了两个问题。

首先，旧 CUDA 12 插件与 CUDA 13 插件同时存在，导致：

ALREADY_EXISTS:
PJRT_Api already exists for device type cuda

因此需要清理旧插件：

python -m pip uninstall \
    jax-cuda12-plugin \
    jax-cuda12-pjrt

其次，JAX 尝试分配较大的 GPU 显存块，而 RTX 3060 只有 6 GB 显存。

为了减少默认显存预分配，我设置：

export XLA_PYTHON_CLIENT_PREALLOCATE=false

此外，检查环境变量时还发现，旧 CUDA 12.9 的路径仍残留在：

LD_LIBRARY_PATH

因此将旧路径清理，并避免把系统 CUDA Toolkit 的 lib64 目录全局加入动态库搜索路径。

对于同时运行 PyTorch、JAX 和 CUDA C++ 程序的开发环境，这一点尤其重要。

目前 JAX 已经能够识别 CUDA GPU，并完成过矩阵计算，但完整的无警告验证仍需要在清理旧插件和环境变量后重新执行。

8. Git、GitHub CLI 与 SSH#

新系统中重新配置了 Git 用户信息，并完成了 GitHub SSH 认证。

git config --global user.name "Yi Cai"
git config --global user.email "your-email@example.com"
git config --global init.defaultBranch main

使用：

ssh -T git@github.com

验证 SSH 连接。

需要注意，GitHub SSH 认证和 GitHub REST API 认证并不是同一回事。

在重新安装 AI4SciComp 开发工具后，asc doctor 显示 Git、CMake、CTest、SSH 和 PATH 均正常，但 GitHub API 因匿名访问达到速率限制而失败。

此前我的解决方案是通过 GitHub CLI 管理 Token，并自动传递给 ASC：

# Load the AI4SciComp GitHub token from GitHub CLI.
if (( $+commands[gh] )); then
    _asc_token="$(gh auth token \
        --hostname github.com \
        --user escapetiger 2>/dev/null)"

    if [[ -n "$_asc_token" ]]; then
        export ASC_GITHUB_TOKEN="$_asc_token"
    fi

    unset _asc_token
fi

在新系统中重新执行：

gh auth login

完成设备授权后，即可继续使用这种方式，而不必将 GitHub Token 明文写入 Shell 配置文件。

9. 恢复科研项目与验证#

开发工具配置完成后，开始从 GitHub 恢复科研项目，包括 asc-devtools 和 asc-cpp。

其中，asc-devtools 已经成功构建并安装，asc doctor 确认了主要本地工具链和 SSH 认证正常。

对于 asc-cpp，计划采用独立构建目录验证 GCC 15 的 CPU 构建：

cmake -S . -B build-gcc15 -G Ninja \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_C_COMPILER=/usr/bin/gcc-15 \
    -DCMAKE_CXX_COMPILER=/usr/bin/g++-15 \
    -DBUILD_TESTING=ON

随后执行：

cmake --build build-gcc15 --parallel 4

ctest --test-dir build-gcc15 \
    --output-on-failure

这里的配置选项仍需根据项目实际的 CMake 结构确认。完整编译和测试结果尚待记录。

10. 一些经验#

这次重装让我重新考虑了科研开发环境的组织方式。

首先，源码与实验结果应该分开管理。Git 适合保存代码、配置和可复现的实验脚本，但不适合无限制地存储大型数值输出。

其次，系统编译器、CUDA Toolkit 和 Python GPU 运行库应该尽量解耦。它们不必使用完全相同的版本，但必须明确各自的兼容性边界。

再次，不要为了使用最新工具而破坏系统默认环境。对于不同的科研项目，固定编译器版本、依赖版本和构建参数，比单纯追求最新版本更重要。

最后，科研开发环境应该是可以重建的。源码通过 Git 管理，Python 依赖通过 Conda 和 pip 记录，C++ 依赖通过 CMake 管理，个人 Shell 配置独立保存。这样即使以后再次迁移系统，也不需要从头回忆每一个配置步骤。

目前，新 Ubuntu 的主要开发工具已经恢复，GitHub SSH 和 ASC 本地工具检查正常。接下来还需要完成 CUDA 13.3 + GCC 15 的完整验证、PyTorch/JAX 的最终 GPU 测试，以及 asc-cpp 的编译和测试。

这次迁移的目标不只是回收磁盘空间，更是建立一个更简洁、可维护、可复现的科学计算开发环境。
