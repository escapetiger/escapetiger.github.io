Recently, I reinstalled the Windows Subsystem for Linux (WSL2), migrated my existing Ubuntu 22.04 development environment to Ubuntu 26.04 LTS, and reconfigured my research and development tools, including C++, CUDA, Python, and GitHub.

The immediate reason for this reinstallation was disk space. My computer has only one 1 TB SSD, and the old WSL installation was taking up nearly 500 GB. Upon investigation, I found that the problem wasn’t entirely due to the WSL virtual disk itself, but rather to the long-term accumulation of research code, compilation outputs, and numerical experiment results.

I took this opportunity to reorganize my entire development environment and document any noteworthy configuration details.

1. WSL Disk Space Analysis#

First, check the actual space used by the file system in the old Ubuntu installation:

df -h /
sudo du -xhd1 / 2>/dev/null | sort -h
du -h --max-depth=1 ~ | sort -h

The results show that the Linux file system actually uses approximately 416 GB, of which:

DirectorySpace used
/home370 GB
/usr19 GB
/opt14 GB
/var14 GB
~/AI4SciComp280 GB
~/.cache26 GB
~/anaconda322 GB

Further inspection of AI4SciComp:

du -h --max-depth=2 ~/AI4SciComp \
    2>/dev/null | sort -h | tail -50

It was found that asc-cpp-evidence alone took up approximately 274 GB.

This directory is primarily related to previous C++ development and automated verification efforts using Codex. A large volume of test results, experimental outputs, and intermediate files has accumulated over time, ultimately resulting in significant storage overhead.

This also suggests that the issue of WSL disk space expansion may not be limited to the inability of ext4.vhdx to shrink automatically. In research environments where numerical experiments run for extended periods, the actual file space usage is often a more significant concern.

2. Backing Up Code and Installing a New System#

I chose to do a clean install of Ubuntu instead of upgrading directly over the old system.

Since I only have the C: drive and don’t have enough free space to store both a complete system image and the new environment at the same time, I’m prioritizing backing up my important research code to GitHub.

I ran into GitHub’s large file limit during the backup process. For example:

dof.dat      181.35 MB
data.mat     279.30 MB

GitHub’s standard Git repositories do not accept individual files larger than 100 MiB. Even if a file is later deleted, it may still cause a push to fail as long as it remains in the Git history to be pushed.

Therefore, source code and large-scale experimental data should be managed separately. Git is suitable for research source code, while large-scale numerical results are better stored in separate archives, using Git LFS or other storage services as needed.

After installing the new system, I named the WSL distribution “Ubuntu” and set it as the default distribution:

wsl --set-default Ubuntu

Next, set Ubuntu as the default terminal in Windows Terminal and continue using Zsh as your everyday shell.

3. Shell and Personal Development Configuration#

To make future migrations easier, I’ve split my personal Shell configuration into separate files:

~/.config/shell/
├── aliases.sh
├── exports.sh
└── functions.sh

Loaded from ~/.zshrc:

source "$HOME/.config/shell/exports.sh"
source "$HOME/.config/shell/aliases.sh"
source "$HOME/.config/shell/functions.sh"

This way, personal shortcuts, environment variables, and custom functions can be maintained independently.

Compared to cramming all the configurations into .zshrc, this approach makes it easier to back up, reuse, and troubleshoot environment issues.

4. C++ Compilation and Build Tools#

The new system uses a newer GNU toolchain.

The current version of G++ in use is:

GCC 15.2.0

CMake has been upgraded to:

CMake 4.4.4

Install Ninja at the same time, as the primary build backend for CMake.

For typical C++ projects, you can use:

cmake -S . -B build -G Ninja \
    -DCMAKE_BUILD_TYPE=Release

cmake --build build --parallel 4

In research projects, I prefer to create separate build directories for different compilers, build modes, and computation backends to avoid CMake cache conflicts between different configurations.

For example:

build-gcc15/
build-debug/
build-cuda/

This also makes it easier to compare performance across different compilers and build parameters.

5. Eigen, oneMKL, and oneTBB#

For linear algebra, I reinstalled Eigen and configured Intel oneMKL and oneTBB.

Eigen 5.0.1#

Eigen is obtained from the official GitLab repository using a fixed version tag:

git clone https://gitlab.com/libeigen/eigen.git
cd eigen
git checkout 5.0.1

When installing via CMake, set the installation prefix to:

/usr/local

The target location for the Eigen header files is:

/usr/local/include/eigen3/

In a CMake project, you can use:

find_package(Eigen3 5.0 REQUIRED NO_MODULE)
target_link_libraries(main PRIVATE Eigen3::Eigen)

Eigen is a header-only library; there is no need to build an optional BLAS/LAPACK-compatible library in order to use its C++ matrix interface.

Intel oneMKL#

For high-performance numerical computations such as BLAS, LAPACK, and FFT, I choose to install Intel oneMKL on an as-needed basis rather than the full oneAPI Toolkit:

sudo apt install intel-oneapi-mkl-devel

MKL is typically installed in:

/opt/intel/oneapi/mkl/latest/

Load when needed:

source /opt/intel/oneapi/mkl/latest/env/vars.sh

oneTBB#

Install the oneTBB task-parallelism library using the Ubuntu software repositories:

sudo apt install libtbb-dev

In CMake, find and link oneTBB as follows:

find_package(TBB CONFIG REQUIRED)
target_link_libraries(main PRIVATE TBB::tbb)

Ultimately, Eigen, oneMKL, and oneTBB are responsible for C++ linear algebra expressions, traditional high-performance numerical libraries, and task parallelism, respectively; all three can be combined as needed based on the specific algorithm requirements.

6. Migrating the CUDA Development Environment#

The CUDA compatibility issues encountered during this migration are particularly worth noting.

My GPU is an NVIDIA GeForce RTX 3060 Laptop with 6 GB of video memory and compute capability 8.6.

Initially, the following was used:

CUDA Toolkit 12.9
GCC 15.2
Ubuntu 26.04

However, when compiling a CUDA C++ program, NVCC directly reports:

unsupported GNU version!
gcc versions later than 14 are not supported!

After trying GCC 14, I encountered another conflict between the declarations of mathematical functions in the CUDA header files and those in the system’s glibc header files, specifically involving:

cospi
sinpi
rsqrt

To try bypassing the GCC version check, I used:

-allow-unsupported-compiler

Even with this flag, the GCC 15 standard library still produces compilation errors such as __is_pointer and __is_volatile.

This indicates that CUDA compatibility depends not only on the GCC version, but also on the NVCC compiler front end, the C++ standard library, and the system’s glibc.

Upgrade NVIDIA Drivers#

After that, I updated the Windows NVIDIA driver to a newer version.

In WSL, nvidia-smi displays:

NVIDIA-SMI: 615.78.05
KMD Version: 617.42
CUDA UMD Version: 13.4

The GPU is recognized properly.

Please note that WSL2 uses the NVIDIA drivers provided by Windows; you should not install standard Linux NVIDIA graphics drivers within Ubuntu.

Installing CUDA Toolkit 13.3#

In the official NVIDIA WSL APT repository, the latest Toolkit version available at the time was 13.3.1.

I chose to pin the installation to this version series:

sudo apt install cuda-toolkit-13-3

And configure it in the shell:

export CUDA_HOME=/usr/local/cuda-13.3
export CUDACXX="$CUDA_HOME/bin/nvcc"
export PATH="$CUDA_HOME/bin:$PATH"

The CUDA architecture parameters for the RTX 3060 are as follows:

-arch=sm_86

Compiling and running a minimal CUDA program using CUDA 13.3 and GCC 15 are key validation items for the migration. Although a test process has already been established, the operational logs on which this record is based do not yet show results indicating a successful execution; therefore, this test is not yet listed as passed.

7. Anaconda and the Python Research Environment#

We will continue to use Anaconda for the Python environment, but we will consolidate research dependencies into a separate environment:

conda create -n sci python=3.12 pip
conda activate sci

The basic scientific computing library includes:

conda install -c conda-forge \
    numpy scipy matplotlib pandas sympy \
    h5py scikit-learn \
    jupyterlab ipykernel \
    tqdm pyyaml pytest

PyTorch and JAX are the primary tools used for GPU computing.

After updating the NVIDIA drivers and the CUDA Toolkit, I went on to try updating both frameworks to CUDA 13.

PyTorch uses the official CUDA wheel, while JAX uses:

python -m pip install -U "jax[cuda13]"

It is important to note that the version of the CUDA runtime library used by the Python framework does not have to match the minor version of the system’s CUDA Toolkit exactly.

JAX GPU Initialization Issue#

We encountered two issues during the JAX upgrade.

First, the old CUDA 12 plugin and the CUDA 13 plugin coexist, which causes:

ALREADY_EXISTS:
PJRT_Api already exists for device type cuda

Therefore, you need to remove the old plugins:

python -m pip uninstall \
    jax-cuda12-plugin \
    jax-cuda12-pjrt

Second, JAX attempts to allocate large blocks of GPU memory, but the RTX 3060 only has 6 GB of VRAM.

To reduce the default video memory preallocation, I set:

export XLA_PYTHON_CLIENT_PREALLOCATE=false

In addition, while checking the environment variables, we found that the path for the old CUDA 12.9 was still present at:

LD_LIBRARY_PATH

Therefore, clear the old paths and avoid adding the system CUDA Toolkit directory lib64 to the global dynamic library search path.

This is particularly important for development environments that run PyTorch, JAX, and CUDA C++ programs simultaneously.

Currently, JAX is able to detect CUDA GPUs and has successfully performed matrix computations; however, a complete, warning-free validation will still need to be rerun after cleaning up old plugins and environment variables.

8. Git, GitHub CLI, and SSH#

Git user information has been reconfigured in the new system, and GitHub SSH authentication has been completed.

git config --global user.name "Yi Cai"
git config --global user.email "your-email@example.com"
git config --global init.defaultBranch main

Usage:

ssh -T git@github.com

Verify the SSH connection.

Please note that GitHub SSH authentication and GitHub REST API authentication are not the same thing.

After reinstalling the AI4SciComp development tools, asc doctor showed that Git, CMake, CTest, SSH, and PATH were all functioning normally, but the GitHub API failed due to hitting the rate limit for anonymous access.

Previously, my solution was to manage tokens using the GitHub CLI and automatically pass them to ASC:

# Load the AI4SciComp GitHub token from GitHub CLI.
if (( $+commands[gh] )); then
    _asc_token="$(gh auth token \
        --hostname github.com \
        --user escapetiger 2>/dev/null)"

    if [[ -n "$_asc_token" ]]; then
        export ASC_GITHUB_TOKEN="$_asc_token"
    fi

    unset _asc_token
fi

Re-execute in the new system:

gh auth login

Once you’ve authorized the device, you can continue using this method without having to write the GitHub token in plain text in your shell configuration file.

9. Restoring Research Projects and Validation#

After configuring the development tools, I began restoring my research projects from GitHub, including asc-devtools and asc-cpp.

Among these, asc-devtools has been successfully built and installed, and asc doctor has confirmed that the main local toolchain and SSH authentication are functioning properly.

For asc-cpp, I planned to use a separate build directory to verify the CPU build with GCC 15:

cmake -S . -B build-gcc15 -G Ninja \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_C_COMPILER=/usr/bin/gcc-15 \
    -DCMAKE_CXX_COMPILER=/usr/bin/g++-15 \
    -DBUILD_TESTING=ON

Then execute:

cmake --build build-gcc15 --parallel 4

ctest --test-dir build-gcc15 \
    --output-on-failure

The configuration options here still need to be verified based on the project’s actual CMake structure. Complete compilation and test results have yet to be documented.

10. Some Insights#

This reinstallation has made me rethink how I organize my research and development environment.

First, source code and experimental results should be managed separately. Git is suitable for storing code, configurations, and reproducible experimental scripts, but it is not suitable for storing large amounts of numerical output without restriction.

Second, the system compiler, the CUDA Toolkit, and the Python GPU runtime should be decoupled as much as possible. They do not need to use exactly the same versions, but their respective compatibility boundaries must be clearly defined.

Third, do not compromise the system’s default environment just to use the latest tools. For different research projects, it is more important to keep compiler versions, dependency versions, and build parameters consistent than to simply pursue the latest versions.

Finally, the research and development environment should be reproducible. Source code is managed via Git, Python dependencies are tracked using Conda and pip, C++ dependencies are managed via CMake, and personal shell configurations are saved separately. This way, even if you migrate systems again in the future, you won’t have to recall every configuration step from scratch.

Currently, the main development tools for the new Ubuntu have been restored, and GitHub SSH and the ASC local tools have been verified as functioning normally. Next, we need to complete full validation of CUDA 13.3 + GCC 15, final GPU testing for PyTorch/JAX, and the compilation and testing of asc-cpp.

The goal of this migration is not only to reclaim disk space, but also to establish a more streamlined, maintainable, and reproducible scientific computing development environment.
